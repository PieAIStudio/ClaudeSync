# Local visibility and verified write targets

## Scope and evidence limits

These are the conservative rules approved by the Owner for this repair. They are not a reverse-engineered specification of Claude Desktop. Installed-package inspection was stopped when tooling blocked it; it was not bypassed. This change uses only already-visible ClaudeSync metadata and synthetic fixtures. The Owner must make the final comparison with the four ordinary conversations visible in their Desktop sidebar. No real conversation, account identifier, title, credential, or screenshot is included in this document or the fixture.

## Counting rules and implementation evidence

| Rule | Evidence / implementation location |
| --- | --- |
| Group login accounts by the first scope component, and require a previously verified organization binding. Never infer the current organization from the folder count, timestamps, titles, or an email alone. A binding whose scope is absent from configuration is also unverified. | `src/core/account-identity.ts: accountIdForScope`; `electron/accounts.ts: managedWorkspace`; `src/core/visibility.ts: verifiedOrganization` |
| The main number counts distinct ordinary CLI session identities in the verified current organization: not archived, not a scheduled run, and not covered by a deletion marker. Transcript availability affects sync eligibility, not visibility. | `src/core/catalog.ts: sessionKey, buildCatalog`; `src/core/visibility.ts: entryGroup` |
| Archive state is the JSON `isArchived` flag OR the configured scope's `archived-sessions.idx` membership. Both full local entry IDs and bare entry IDs are accepted. Old scopes cannot override current archive state. | `src/core/workspace.ts: archivedSessions, loadWorkspace`; `src/core/visibility.ts: entryGroup` |
| A nonempty `scheduledTaskId` identifies a scheduled run. Similar titles, daily timestamps, and single-turn length do not. Unknown non-string task-ID formats cause that index to be skipped and reported unchanged, rather than blocking other chats or pretending to be ordinary records. | `src/core/record.ts: validateSessionRecord`; `src/core/visibility.ts: entryGroup` |
| Native `deleted_<id>` markers in configured scopes of the same login suppress matching entries and history lineage from the main count. Another login's marker does not hide this login's rows. The cross-account anti-resurrection guard remains for bulk keep-only; explicit selected sync may clear the selected lineage's relevant notes in participating accounts after checking all other eligibility guards. | `src/core/visibility.ts: deletionMarkers, hasDeletionMarker`; `src/core/workspace.ts: entryEligibility`; `src/core/planner.ts: buildPlan` |
| Classification per copy is deleted first; a different organization is old only with explicit retirement evidence, otherwise unverified; current copies are scheduled, archived, then ordinary or organization-unverified. Main counts are null, not zero or an estimate, without a usable verified organization. | `src/core/visibility.ts: entryGroup`; `src/core/catalog.ts: buildCatalog` |
| Archive, scheduled-run, old-organization, deleted-session and unverified groups are separate and initially collapsed. Per-group projection excludes other groups' titles, states and copies before selection. | `src/renderer/session-groups.ts: sessionsInGroup`; `src/renderer/components.tsx: AccountSidebar, CollapsedSessionGroup`; `src/renderer/App.tsx` |

Each group deduplicates by the existing CLI session identity. The same identity may have a current copy and an old-organization copy, so group counts must not be added to infer a distinct-session total. The deleted-session group counts only surviving indexed sessions. Raw distinct marker-ID counts are not presented as session counts. Cloud counts remain separate. Unsupported scheduled/remote records direct the user to Claude rather than allowing unsafe task edits.

The organization binding is the last successful profile verification remembered locally, not a claim that an offline scan freshly queried Desktop's UI. The 2026-11-01 cloud review corrected an unsafe inference: verifying one current organization does not retire any other organization. The current profile adapter cannot prove retirement and never creates retirement evidence; unproven scopes stay unverified and out of old-copy cleanup. Synthetic old-copy scenarios explicitly provide retirement evidence, and separate tests protect two live organizations. Switch accounts in Desktop and refresh to establish or update a binding. Email-only identities remain unverified. The earlier visibility repair added no credential-access mechanism. The 2026-11-01 follow-up uses an in-process native Keychain adapter with mocked credential tests only; it did not access the Owner's real Keychain.

## Why old organizations could receive copies

The preserved migration baseline is commit `1e1c7a1`. In that baseline, `electron/accounts.ts: managedWorkspace` kept every configured scope when the identity cache had no organization. `src/core/planner.ts: buildPlan` iterated every configured scope as an independent destination. `src/core/operations.ts: buildOperationPlan` required keep-only coverage in every included folder; its regression test explicitly expected writes into duplicate organization folders.

This is a reproduced mechanism capable of producing the reported old-organization copies. It is not a forensic claim about the exact provenance of individual historical files; those real files were not read.

## Write boundary

`verifiedTargets` requires one usable verified current organization for every included destination login. Sync and keep-only refuse the entire plan if any destination is unknown or missing; they never silently skip the uncertain account. Additions, title changes and keep-only archive changes are constrained to verified current scopes. The transaction boundary rejects old-scope record writes. Explicit sync has a narrow exception for reviewed removal of relevant native deletion notes in participating accounts' old scopes.

Recognized inventory is scanned for path safety and shared-history claims. Unknown entries are skipped without following links or reading opaque stores, and their relative paths appear under Needs attention as skipped and unchanged. Known Desktop `backlog` and `waiting-input` stores are retained but never managed or counted. If skipped entries could hide shared references, deletion preserves transcript bodies. Unsafe actual write targets still stop the affected operation. Selected deletion and old-copy cleanup compare only relevant data dependencies; unrelated body/index changes no longer invalidate the displayed selection. Organization bindings and retirement evidence are included in the displayed revision and checked again during application. An organization change invalidates an old selection or preview.

Explicit archive, rename, star and deletion actions are scoped to the selected group. A current-group selection does not silently edit an old copy. Sync source paths are also pinned to the selected group: an ineligible archived selection cannot silently borrow a same-ID old copy. Keep-only may unarchive an existing selected-ID counterpart in a verified current target, but never unarchives the old source in place. Shared entry IDs normally prevent unsafe partial deletion. Explicit old-copy deletion may remove an old index with a verified current counterpart without deleting shared bodies or marking shared IDs as deleted. Selecting an old copy as a sync source may create a copy in a verified current target, but never updates old session indexes in place. Scheduled runs remain unsupported. Surviving deletion-marked entries can be selected for explicit sync only; other editing actions do not implicitly restore them.
